# UT 审查入口

先明确审查范围、代码状态及静态/执行审查授权。Review 默认不改被审查文件；执行检查应在不污染用户改动的条件下进行，存在外部写入/付费行为时不自动运行。

## 按规则取证

1. 从用户请求、Diff、接口和行为找适用 UT 规则，而非先跑固定全仓清单。
2. 逐项读取最小足够证据：实现、测试、配置、日志和项目约定。相关日志缺失则运行允许的检查或标记 UNKNOWN。
3. 检查测试是否验证契约，Mock 是否掩盖目标，关键失败能否触发断言。覆盖率与用例数量不能代替这些判断。
4. 检查真实范围、运行完整性、代码快照和门禁是否一致。独立运行与套件运行仅在需要判断污染时追加。
5. 把具体问题对应规则编号、位置、触发路径、影响与建议；不要将偏好写成违规。

## 判定

- PASS：有足够证据支持本条要求。
- FAIL：有具体违规事实；说明为什么能触发影响。
- NOT_APPLICABLE：适用条件不成立，写理由。
- UNKNOWN：证据不足、无法运行、基线未知或关键预期无法确认；不得转为 PASS。

静态审查可以证明某项代码约束满足，但不能证明未执行测试已通过。全范围审查需要覆盖适用规则集，局部审查只报告局部结论，不声称全项目 UT 合格。

## 输出

```text
范围/代码状态/审查方式：
结论：测试质量、实际执行结果、任务完成度分别说明；仅静态审查时不声称运行通过
问题：[规则编号] 文件:行 — 触发条件、影响、证据、建议
未知项：缺失证据和最小补充动作
已执行验证：真实命令与结果
例外：规则、批准记录、有效范围与撤销条件
```

重要问题优先；不存在问题不必制造建议。仅说明使用同一 Agent 自审时，不写“独立审查通过”。

缺陷状态和报告字段见 [结果记录](result-recording.md)；质量规则结论不得直接代替测试执行结果。
