# 结果记录与判定

仅在整理运行结果、缺陷记录或最终报告时读取。字段可按任务裁剪，但未知、未执行与失败不得隐藏。

## 缺陷状态

| 状态 | 使用条件 |
| --- | --- |
| candidate | 有具体疑点，待验证 |
| confirmed | 正确期望和触发有依据，真实失败可归因 |
| not_reproduced | 当前探测未复现，尚无充分反证 |
| dismissed | 反证已证明候选不成立，附反证 |
| inconclusive | 证据不足或失败不稳定 |
| report_only | 静态证据充分，但没有运行确认 |

探测通过时检查触发路径、Mock 有效性和断言敏感性；不足时不能 dismissed。业务缺陷 confirmed 与测试规则 FAIL 不是同一含义：正确断言暴露业务错误，可以满足 UT-06、UT-16、UT-22。

## 三类结论分开

- 测试质量：适用规则均 PASS/N/A 且没有遗漏要求，才称合格；规则 FAIL 为不合格，UNKNOWN 为待验证。
- 执行结果：报告实际通过、失败、跳过、预期失败及未执行；业务缺陷失败仍是执行失败。
- 任务完成度：按约定范围判断完成、部分完成或阻塞；补测任务可在保留业务缺陷复现后完成，不表示执行通过。

`gate_report.py` 的 READY/NOT_READY/BLOCKED 仅汇总输入的质量规则：READY 为给定规则均满足，NOT_READY 为存在违规，BLOCKED 为缺证据或全部不适用。它不读取运行结果，不检查范围是否完整，不是执行/合并/发布门禁。不要仅因发现业务 Bug 就填某条质量规则 FAIL；按该条是否满足填报。

## 最小报告

```text
范围与被测代码状态：
行为 / 正确预期依据 / 测试位置：
基线及差异（需要时）：
命令 / 工作目录 / 退出码 / 发现数 / PASS / FAIL / SKIP / XFAIL / 未执行：
缺陷状态与证据（有则列出）：
覆盖率口径 / 阈值 / 完整性 / 结果（需要时）：
规则编号 / 判定 / 证据 / 例外：
测试质量：合格 / 不合格 / 待验证 / 有批准例外
执行结果：通过 / 失败 / 未完成 / 未执行
任务完成度：完成 / 部分完成 / 阻塞
```

计数使用用例、Subtest 或参数化项时保持一致；不同工具无法对齐则分组，不把断言数量当用例数。复跑、顺序或并行对照仅在有相关风险时追加，不靠固定次数“证明”确定性。

例外不自动抹除原 FAIL/UNKNOWN；脚本不支持自动批准例外，需人工记录批准与补偿措施。框架支持时以限定失败原因及 strict 模式管理预期失败，不能宽泛捕获所有异常。
